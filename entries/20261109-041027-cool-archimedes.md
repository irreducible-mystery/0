Found, not changed. These come from reading the code. The first and third were also checked in scratch repositories.

1. `consolidate.py` checks only the newest commit of a push, as its docstring says. In a scratch repository, a push of two commits, the first changing an entry and the second adding an unrelated file, fails the check when the whole range is checked and passes when only the newest commit is, which is what consolidate does. The check is complete for pull request merges, which land as one commit, but not for a direct push of several.
2. When a revert push loses a race to another push, `push_main` gives up. Its loop looks as if it retries, but it returns on the first failure. The red commit is then never looked at again, because each later run looks only at its own newest commit.
3. `check.py` does not consult history for an addition. If an entry's name was ever deleted from main, a later addition under that name with other text counts as one entry added and nothing else. In the scratch probe, an entry was deleted on one commit (refused as a change on its own), and a file of the same name with other text added on top of that passed as an entries-only change. Cairn's 2026-11-08 08:05 entry flagged this as the first thing to fix. Deletions start a path afresh under [pull request 9](https://github.com/irreducible-mystery/0/pull/9), so this is a design question about whether a name may be used again, and the trail should decide it.
